# 商家端下单设计评审（基于当前代码）

> 评审范围：`ruoyi-admin` 模块下 `com.ruoyi.merchant` 包的下单、支付、发货相关流程。

## 总体结论

当前实现已经具备「商品查询 -> 下单 -> 支付（mock） -> 发货」的主链路，分层（Controller / Service / Manager / Mapper）也基本清晰，能支撑个人项目的功能迭代。

但从**一致性、并发、可演进性**角度看，仍有几个关键设计风险，建议优先修复：

1. **订单状态机不闭环**：创建后状态与支付入口校验不一致，导致流程卡住。
2. **参数校验入口不完整**：部分 `@RequestBody` 未触发 Bean Validation。
3. **并发控制过重且含固定 sleep**：会显著拖慢吞吐并放大锁争用。
4. **库存扣减为逐条更新**：多商品订单下性能和失败补偿复杂度偏高。
5. **接口路径与命名不够 RESTful**：后续前后端协作和文档维护成本会上升。

---

## 发现的问题与建议

## 1) 订单状态机存在断点（高优先级）

### 现象
- 下单成功后，订单状态写入 `ORDER_CREATED(1)`。
- 支付接口仅允许 `ORDER_NOT_PAY(2)` 状态进入支付。

### 风险
- 新建订单无法直接支付，业务链路出现「创建成功但不可支付」的断点。

### 建议
- 方案 A（推荐）：将 `createOrder` 写入状态改为 `ORDER_NOT_PAY`。
- 方案 B：保留 `ORDER_CREATED`，但支付前置校验放宽为 `ORDER_CREATED` 或 `ORDER_NOT_PAY`。
- 同时补一组状态流转单测（创建->支付->发货，及非法状态转移）。

---

## 2) 请求参数校验未完全生效（高优先级）

### 现象
- `merchantCreateOrder` / `deliver` / `pay` 这几个接口的 `@RequestBody` 参数未标记 `@Validated`（或 `@Valid`）。
- `MerchantOrderCreateReq` 中存在看起来已不再使用的字段（如 `productId`、`num`），且类型与注解不匹配（`String` + `@Min`）。

### 风险
- 无效请求可直接进入业务层，错误在深层抛出，排障和前端联调成本较高。

### 建议
- 在 Controller 层统一补齐 `@Validated`。
- 清理订单创建请求中的冗余字段，只保留 `orderProductDTOList` 作为商品明细入口。
- 对数量字段使用 `Integer + @Min(1)`，避免语义歧义。

---

## 3) 并发下单实现成本偏高（高优先级）

### 现象
- 下单前对每个商品加分布式锁并排序，思路是对的。
- 但锁内存在固定 `sleep(10s)`。

### 风险
- 任何订单都会额外阻塞 10 秒，直接降低吞吐。
- 高并发下更容易触发 `tryLock` 失败，用户侧感知「系统繁忙」。

### 建议
- 移除固定 sleep。
- 保留「按商品 ID 排序后加锁」策略。
- 中长期建议改为「数据库原子扣减 + 最小锁粒度」或「异步下单（消息队列）」。

---

## 4) 库存扣减与订单写入的事务策略可优化（中优先级）

### 现象
- 当前库存扣减为逐个商品循环 update。
- 已有批量扣减方法雏形，但下单链路未使用。

### 风险
- 多商品订单时 SQL 次数线性增长。
- 某一商品扣减失败时，补偿路径依赖事务回滚，锁持有时间也更长。

### 建议
- 优先将逐条扣减改为批量扣减（单 SQL 或批处理）。
- 明确失败语义：是「整体失败回滚」还是「返回缺货明细并部分成功」；目前更接近前者。

---

## 5) API 设计可继续标准化（中优先级）

### 现象
- 接口命名偏动作式（如 `/getMerchantList`、`/merchantCreateOrder`）。
- 路由前缀包含 `/RuoYi/merchant`，大小写与生态常见习惯不同。

### 风险
- 随接口增多，语义统一性下降；自动化文档和 SDK 生成体验一般。

### 建议
- 渐进改造为资源式接口，例如：
  - `GET /api/merchant/products`
  - `GET /api/merchant/products/{id}`
  - `POST /api/merchant/orders`
  - `POST /api/merchant/orders/{id}/pay`
  - `POST /api/merchant/orders/{id}/shipments`
- 旧接口保留一段时间并做兼容映射，避免一次性改动过大。

---

## 6) 你目前设计里做得不错的点（可保留）

1. **分层明确**：Controller 不直接写 DB，Service 编排 + Manager 落地，后续可扩展。
2. **商品锁顺序化**：通过排序避免交叉加锁死锁，方向正确。
3. **价格策略模式**：`PriceStrategyFactory + Strategy` 对客户类型差异计价很实用。
4. **订单商品快照**：下单时记录商品名、价格快照，后续审计和售后可追溯。

---

## 建议的三步落地计划（低成本）

### 第 1 步（1 天内）
- 修复状态机断点（创建态与支付态一致）。
- Controller 补齐 `@Validated`。
- 删除 `sleep(10s)`。

### 第 2 步（1~2 天）
- 清理 `MerchantOrderCreateReq` 冗余字段与校验。
- 下单链路切换到批量扣减库存。
- 补最小回归测试：正常下单、库存不足、并发下单。

### 第 3 步（按需）
- 统一 API 路由命名。
- 引入状态机组件或状态流转守卫，避免未来状态膨胀后失控。

---

## 一句话结论

你的当前设计**没有方向性错误**，对个人项目来说可用；但如果你准备继续做真实流量或多人协作，建议优先处理「状态机一致性 + 参数校验 + 锁内 sleep」这三项，它们是当前最容易导致线上问题的点。
